# 多页面多工序隔离能力审计报告 v1

## 1. 文档目的

本报告用于审计当前系统是否满足以下业务前提：

- 同一个功能下可以打开多个不同页面
- 每个页面绑定独立工序
- 每个页面可独立绑定模型
- 每个页面可独立执行规则判定
- 页面之间不能互相干扰

本报告聚焦当前项目中的 OCR 检测主链路，审计范围包括：

- 前端页面状态管理
- 模型选择与模型调用链路
- 实时检测请求链路
- 结果保存链路
- 后端结果模型

## 2. 审计结论

结论：**当前实现不满足“多页面按工序独立绑定模型与规则，且彼此互不干扰”的要求。**

当前系统的真实状态是：

- 同类页面共享同一套 OCR 持久化配置
- 页面模型配置不是完整页面隔离
- 后端检测调用主要按 `detection_type` 路由，不是按页面独立模型调用
- 保存结果时没有记录工序标识、页面标识、工装二维码等关键追踪字段

因此，现阶段即使页面表面上能同时打开，也不能认为已经实现了“多页面独立工序系统”。

## 3. 总体风险评估

### 3.1 审计评级

- 架构符合度：低
- 多页面隔离能力：低
- 多工序独立建模能力：低
- 误判和串扰风险：高
- 直接上线适配你目标场景的可行性：不建议

### 3.2 结论摘要

当前系统最大的问题不是“页面不能打开多个”，而是：

- 多页面打开后共享关键配置状态
- 页面选择的模型不一定真正传到后端执行
- 工序身份没有沉淀进结果数据
- 后端无法可靠地区分同功能下不同页面的工序身份

## 5. 失败场景分析

以下是当前架构下非常可能出现的失败场景。

### 5.1 页面配置串扰

场景：

- 页面 A 绑定工序1，选择模型 M1
- 页面 B 绑定工序2，选择模型 M2
- 页面 A 修改 `selectedTargets`

结果：

- 页面 B 可能读取到页面 A 的持久化配置
- 导致模型、目标、规则被覆盖

### 5.2 后端实际运行模型与页面选择不一致

场景：

- 页面 A 和页面 B 都属于 `ocr_inspection`
- 页面 A 希望跑模型 A
- 页面 B 希望跑模型 B

结果：

- 后端仍可能统一映射到 `waterprifer_detection`
- 两页实际跑的是同一个 YOLO 模型

### 5.3 结果落库后无法追责

场景：

- 多个工序页面同时运行
- 后端保存了一批 `ocr_inspection` 结果

结果：

- 无法从结果中区分这条记录属于哪个工序
- 无法根据工装二维码建立追踪链
- 无法为跨工序规则提供稳定输入

### 5.4 工序 UI 存在但数据层不存在

场景：

- 页面上展示“工序1/工序2”
- 用户以为系统已经按工序建模

结果：

- 实际只是 UI 文案区分
- 数据结构仍是共享的 OCR 检测结果

## 6. 根因分析

### 6.1 根因一：状态作用域设计错误

当前 OCR 页面配置被设计为：

- 全局共享
- localStorage 持久化

但业务需要的是：

- 页面级
- 工序级
- 或页面实例级

### 6.2 根因二：模型调用没有显式化

当前模型调用更多依赖：

- `detection_type`
- 后端默认模型

而不是：

- 页面显式指定 `model_id`

### 6.3 根因三：工序上下文没有进入结果模型

当前系统把“工序信息”停留在页面层，没有进入：

- 保存模型
- API 结构
- 审计结果

### 6.4 根因四：追踪业务尚未正式建模

当前系统还没有“工装二维码追踪链”正式模型，所以无法天然支持：

- 同工装多工序归并
- 跨工序规则计算
- 工序追踪结论输出

## 7. 这是否算“已经实现”

答案：**不算。**

更准确地说，当前实现只达到以下程度：

- 同一功能页面可以多开
- 摄像头层面有部分窗口区分
- 页面可以显示不同内容

但没有达到以下要求：

- 页面级状态隔离
- 工序级模型隔离
- 工序级规则隔离
- 多工序追踪数据落库
- 后端基于工装二维码做稳定归并

## 8. 是否存在“看起来实现了但实际上会失败”的情况

答案：**存在，而且概率很高。**

主要表现为：

- UI 上切了模型，但后端没按这个模型执行
- 页面上写了工序名，但落库结果里没有工序字段
- 页面 A 改了配置，页面 B 被动串扰
- 结果页里多条记录看起来都一样，后续无法复盘

## 9. 整改目标

要满足你的业务前提，至少必须实现以下能力：

### 9.1 页面实例级隔离

对同功能页面做配置分片，分片键建议至少包含：

- `page_instance_id`
或
- `process_stage_code`

不能继续所有页面共享一份 `ocr-detection-storage-v2`。

### 9.2 模型调用显式化

前端检测请求必须明确传：

- `model_id`

不能只传：

- `detection_type`

### 9.3 工序上下文落库

结果模型必须新增：

- `process_stage_code`
- `process_stage_name`
- `page_instance_id`
- `camera_id`
- `fixture_qr`
- `fixture_qr_source`
- `fixture_qr_input_status`
- `trace_conclusion`
- `trace_rule_details`

### 9.4 保存链路补全追踪信息

保存结果时必须把：

- 工序标识
- 页面标识
- 相机标识
- 工装二维码
- 追踪规则结论

一起传到后端。

### 9.5 OCR 和 LLM 配置也要支持工序独立

不同工序可能使用不同：

- OCR 引擎
- YOLO 模型
- LLM 模型
- 提示词模板

因此这些配置不能继续完全全局共享。

## 10. 整改优先级建议

### P0：必须先做

1. 页面状态隔离
2. 显式模型调用
3. 结果模型增加工序与追踪字段
4. 保存链路补工序和工装二维码

### P1：紧随其后

1. 追踪判定服务
2. 工装二维码规则
3. 跨工序规则最小版本
4. 结果区追踪说明展示

### P2：后续增强

1. 可视化规则编辑器
2. 多来源追踪码输入切换
3. 历史追踪审计看板
4. 异常转绑流程

## 11. 建议的下一步动作

建议按以下顺序推进攻克：

1. 先完成页面级配置隔离设计
2. 再改实时检测请求，改为按页面传 `model_id`
3. 再给结果模型补字段
4. 再补前后端保存与展示链路
5. 最后接入工装二维码追踪规则

## 12. 最终审计结论

当前系统尚未实现你要求的核心大前提：

`同功能的不同页面按工序独立绑定模型与判定规则，并且相互之间完全不干扰`

如果不整改，未来在多页面、多工序、多工装同时流转场景下，极有可能出现：

- 模型串扰
- 规则串扰
- 结果串工序
- 审计不可追溯
- 追踪规则无法可靠落地

因此，本问题应视为当前架构中的 **P0 级阻塞问题**。

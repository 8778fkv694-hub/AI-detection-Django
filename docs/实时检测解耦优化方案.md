# 实时检测解耦优化方案

> 创建日期：2026-05-12
> 状态：待实施
> 目标设备：Jetson Orin Nano（主力），兼容其他设备

---

## 1. 问题背景

### 1.1 当前痛点

Jetson Orin Nano 上运行时存在以下问题：

| 问题 | 根因 | 影响 |
|:---|:---|:---|
| CPU 被塞死，卡顿严重 | MJPEG 编码（`cv2.imencode`）纯 CPU 操作，1080p quality=95 单帧 80-150ms | 整机响应迟钝 |
| GPU 利用率低 | YOLO 推理用 PyTorch `.pt` 格式，未用 TensorRT | GPU 算力浪费 70% |
| 外接显示器画面不流畅 | 前端浏览器同时做 ONNX YOLO 检测 + Canvas 画框 + MJPEG 解码 | 浏览器吃满 CPU |
| 检测频率低（~2fps） | 前端 `setInterval(500ms)` 截图 → Base64 上传（100-500KB）→ 等后端返回 | 受前端轮询限制 |
| 摄像头/画框/检测三者耦合 | 前端同时承担：视频采集、YOLO 检测触发、Canvas 画框、业务判断 | 维护困难，资源竞争 |

### 1.2 优化愿景

- **后端检测要快**：YOLO 检测持续高频运行（20+fps），充分利用 GPU
- **前端显示可以慢**：人眼看到的画面 10-12fps 即可，不占用过多资源
- **检测频率 ≠ 显示频率**：彻底解耦
- **前端只负责展示**：不分担推理压力
- **支持多摄像头**：2-3 个摄像头在不同页面同时检测
- **保留现有业务逻辑**：选中目标、OR/AND 模式、批处理触发等全部保留

### 2.2 两套检测流程（❌ 需改造）

项目中存在**两套独立的前端检测流程**：

#### 流程 A：LiveInspection（安全装备检测）

```
入口：useLiveYoloDetection.ts（351 行）
触发：setInterval(500ms) → 固定 2fps
流程：前端截图 → Base64 上传 → yoloDetectBackend() → 返回 boxes
         → OR/AND 判断 → 自动抓拍 → AI 分析
画框：前端 Canvas 画框（useLiveYoloDetection.ts 第 292-344 行）
```

#### 流程 B：OCRDetection（实时检测模式）

```
入口：useRealtimeDetectionLoop.ts（1036 行）
触发：setInterval(detectionInterval) → 可配置频率
流程：前端截图 → Base64 上传 → yoloDetectBackend() → 返回 boxes
         → evaluateDetections() OR/AND 判断
         → evaluateDebounce() 防抖
         → ROI 裁剪 + 清晰度评估
         → 批处理模式：cacheROI → triggerBatchProcessing
         → 非批处理：拼接 → processCapturedImage
画框：drawDetections() 绘制到检测 Canvas
```

#### 共同问题

```
前端 drawImage(video) → toDataURL('image/jpeg') → split(',')[1]
      → yoloDetectBackend(base64Image, conf)
      → POST /api/yolo/detect/  (100-500KB Base64)
      → 等待后端 YOLO 推理
      → 返回 boxes JSON
```

**每次检测传输 100-500KB 的 Base64 图片，后端 `StreamReader` 里明明已经有 `current_frame` 却不用。**

### 2.3 前端 ONNX 检测器（❌ 应禁用）

- `src/lib/onnxYoloDetector.ts` — 前端加载 ONNX 模型跑 YOLO
- `src/lib/yoloDetector.ts` — 前端 ONNX Runtime 双引擎

在 Jetson 浏览器上运行会严重占用 CPU，与"前端不分担压力"目标矛盾。

## 3. 改造方案

### 3.1 架构总览

```
改造前（耦合）：
─────────────────────────────────────────────────────
  摄像头 → StreamReader → MJPEG（纯画面，无框）
                                     前端 <img> 显示
  前端每 500ms：
    截图(drawImage) → Base64(100-500KB) → POST → YOLO → JSON
                                     前端 Canvas 画框
─────────────────────────────────────────────────────

改造后（解耦）：
─────────────────────────────────────────────────────
  摄像头 A → StreamReader A → current_frame (共享)
                                    ↓
                          DetectionLoop A（后台线程）
                          YOLO 高频检测（20+fps）
                                    ↓
                    ┌───────────────┼───────────────┐
                    │               │               │
             latest_boxes    MJPEG 带框流     /snapshot/
                    │          12fps            高清截图
                    ↓               ↓               ↓
          /api/.../detections/  前端 <img>    ROI 裁剪用
          JSON (<1KB)           (带框画面)
                    ↓
          前端业务逻辑（不变）
          OR/AND 判断、批处理触发
─────────────────────────────────────────────────────

  摄像头 B → StreamReader B → DetectionLoop B → 同上
  摄像头 C → StreamReader C → DetectionLoop C → 同上
─────────────────────────────────────────────────────
```

### 3.2 改造原则

1. **后端做重活**：YOLO 推理、画框全在后端
2. **保留现有触发逻辑**：前端的 OR/AND 判断、防抖、批处理触发等业务逻辑**不动**
3. **只改数据来源**：从"前端截图上传"改为"拉取后端 JSON"
4. **多摄像头支持**：每个 `stream_id` 对应一个独立检测循环

## 4. 后端改动明细

### 4.1 [新建] `backend/inspection/detection_loop.py`

持续检测管理器，每个 stream 对应一个独立检测线程。

```python
class DetectionLoop:
    """单个流的持续检测循环"""

    def __init__(self, stream_id, model_id, conf_threshold=0.5):
        self.stream_id = stream_id
        self.model_id = model_id
        self.conf_threshold = conf_threshold

        self.latest_boxes = []           # 最新检测结果
        self.latest_frame_jpeg = None    # 最新帧的 JPEG（供 /snapshot/ 用）
        self.detect_fps = 0.0            # 实际检测帧率
        self.is_running = False
        self._lock = threading.Lock()
        self._thread = None

    def start(self):
        """启动检测线程"""
        self.is_running = True
        self._thread = threading.Thread(target=self._detect_loop, daemon=True)
        self._thread.start()

    def _detect_loop(self):
        """核心检测循环"""
        from .stream_service import stream_manager
        from .yolo import run_inference

        while self.is_running:
            reader = stream_manager.get_stream(self.stream_id)
            if not reader or not reader.is_connected:
                time.sleep(0.5)
                continue

            frame = reader.get_frame()
            if frame is None:
                time.sleep(0.01)
                continue

            t0 = time.time()
            boxes = run_inference(frame, conf=self.conf_threshold, model_id=self.model_id)
            elapsed = time.time() - t0

            with self._lock:
                self.latest_boxes = boxes
                self.detect_fps = 1.0 / max(elapsed, 0.001)
                self.latest_timestamp = time.time()

                # 缓存一帧 JPEG 供 /snapshot/ 使用
                _, jpeg = cv2.imencode('.jpg', frame, [cv2.IMWRITE_JPEG_QUALITY, 95])
                self.latest_frame_jpeg = jpeg.tobytes()

    def get_latest(self):
        """获取最新检测结果"""
        with self._lock:
            return {
                'boxes': self.latest_boxes,
                'detect_fps': round(self.detect_fps, 1),
                'timestamp': self.latest_timestamp,
                'model_id': self.model_id,
            }


class DetectionLoopManager:
    """管理多个流的检测循环（单例）"""
    _instance = None

    def start_loop(self, stream_id, model_id, conf):
        """启动指定流的检测循环"""
        ...

    def stop_loop(self, stream_id):
        """停止指定流的检测循环"""
        ...

    def get_latest_boxes(self, stream_id):
        """获取指定流的最新检测框（给 MJPEG 画框用）"""
        ...

    def get_snapshot_jpeg(self, stream_id):
        """获取指定流的高清截图 JPEG（给 ROI 裁剪用）"""
        ...
```

**关键约束**：
- 检测线程从 `StreamReader.get_frame()` 取帧，**不另开摄像头**
- `latest_boxes` 只保留最新一帧结果，旧的直接丢
- 支持动态更换 `model_id` 和 `conf_threshold`
- `DetectionLoopManager` 是单例，管理所有流的检测循环

## 11. 蓝军深度评估与架构修正 (Red Team Report)

### 11.1 致命隐患排查

在仔细审视上述初步方案后，我们发现了在 Jetson Orin Nano 这种边缘设备上可能导致系统崩溃的 4 个深层隐患：

#### 隐患一：`cv2.imencode` 阻塞 YOLO 线程（性能倒退）
- **原方案盲点**：为了提供 `/snapshot/` 高清原图，在 `_detect_loop` 的 `while` 循环里加上了 `_, jpeg = cv2.imencode(...)`。
- **致命后果**：在 Orin Nano 的 CPU 上，单核 `imencode` 1080p 图片需要 80-150ms。这会导致即使 TensorRT YOLO 推理只要 30ms，整个循环也会被拖慢到 7fps 以下。这完全违背了“后端高频检测”的初衷。
- **架构修正**：**绝对禁止在检测线程中编码图片**。`/snapshot/` 接口应由另一个独立的缓冲池提供，或者在被请求时现场从内存阵列中异步压码。

#### 隐患二：画面与检测框的“幽灵漂移”（时序错位）
- **原方案盲点**：前端拉取 `/snapshot/` 用于 ROI 裁剪，但裁剪依据的坐标是先前拉取的 `/detections/` 里的框。
- **致命后果**：如果传送带物体移动快（如 1m/s），由于异步获取，`/snapshot/` 拿到的最新帧，与产生 detection 框的那一帧，中间有 200ms 的时间差。这意味着切出的 ROI 会偏离 20cm，导致 OCR 完全切错位置。
- **架构修正**：实现**帧原子性 (Frame Atomicity)**。`DetectionLoop` 必须给每一帧打上唯一的 `frame_id`。`/detections/` 返回带 `frame_id` 的框，前端请求 `/snapshot/?frame_id=xxx`，后端必须返回**产生那个检测框的绝对原始帧**。

#### 隐患三：浏览器内存泄漏 (Out of Memory)
- **原方案盲点**：前端 `URL.createObjectURL(snapshotBlob)` 在延时抓拍的循环中（200ms 一次）被频繁调用。
- **致命后果**：每次 `createObjectURL` 都会在浏览器内存中分配空间。如果不配对使用 `URL.revokeObjectURL()`，几分钟内 Orin Nano 的浏览器就会内存耗尽崩溃。
- **架构修正**：在 React Hooks 中必须严谨管理 Blob URL 生命周期，使用完毕立即清理。

#### 隐患四：HTTP 轮询风暴（打挂 Django 同步网关）
- **原方案盲点**：前端以 10fps 轮询 `/detections/`。如果接入 3 个摄像头，就是每秒 30 个并发请求。
- **致命后果**：Django 和 Gunicorn 默认是同步 worker，高频短连接会耗尽 worker 池，并大量占用 CPU 解析 HTTP 报文，甚至导致正常的抓拍或 AI 分析请求被阻塞。
- **架构修正**：必须控制前端轮询频率（例如降至 3fps 封顶），因为业务逻辑的 OR/AND 判断并不需要 30Hz 的反应速度。或者改用 WebSocket 流式推送（改造稍大，可作为二期优化）。

### 11.2 模型调度瓶颈
- **原方案盲点**：多摄像头支持。
- **致命后果**：Jetson Orin Nano 是统一内存 (Unified Memory)。如果 3 个摄像头用 3 个不同的 YOLO 模型，且 `MAX_POOL_SIZE` 不够，会导致模型在显存和内存间频繁换页 (Thrashing)，整个系统卡死。
- **架构修正**：强制约束 `yolo.py` 中的 `MAX_POOL_SIZE` $\ge$ 活跃摄像头数量。如果显存不足，需实现排队机制，而不是强制换页。

### 11.3 蓝军最终结论
**此方案大体方向（YOLO 后端化、解除前端耦合）是唯一正确的出路。** 但上述隐患如果不加入实施清单，必定在部署时“翻车”。实施第一阶段（Phase 1）必须先解决**帧原子性缓存**和**无阻塞检测循环**的设计。

# 零代码增长功能开发指南

> **核心理念**: 在不增加或少增加代码的前提下实现新功能,通过**重用、配置、组合、替换**策略避免代码膨胀
> **目标**: 让代码库保持精简,功能越来越强,但代码行数趋于稳定甚至减少
> **最后更新**: 2025-01-18

## 🎯 为什么要零代码增长

### 代码膨胀的真实成本

| 问题 | 表现 | 影响 |
|------|------|------|
| **阅读成本** | 单文件超过 3000 行 | 新人上手困难,修改耗时增加 3-5 倍 |
| **维护成本** | 同一逻辑散落在 10+ 个地方 | 修复 bug 需要改 10 个文件,易遗漏 |
| **测试成本** | 重复代码难以统一测试 | 测试覆盖率低,隐藏 bug 多 |
| **性能成本** | 打包体积持续增长 | 首屏加载时间增加,用户体验下降 |
| **心智成本** | "这个功能在哪儿实现的?" | 开发者信心下降,产生"重写冲动" |

### 零代码增长的收益

| 收益 | 具体表现 | 量化指标 |
|------|---------|---------|
| **可维护性** | 修改一处,全局生效 | Bug 修复时间减少 80% |
| **可复用性** | 新功能 80% 代码来自复用 | 开发时间减少 60% |
| **可测试性** | 核心逻辑集中,易于测试 | 测试覆盖率提升至 80%+ |
| **代码质量** | 强制思考设计,避免临时方案 | 代码审查通过率提升 50% |
| **团队协作** | 清晰的模块边界 | 合并冲突减少 70% |

## 🚀 四大核心策略

### 策略 1: 重用优先 (Reuse First)

**理念**: 在写第一行新代码之前,先找找有没有现成的

**三步检查法**:
```
第1步: 项目内搜索 - "有没有类似的功能?"
第2步: 模块库检查 - "hooks/、components/ 下有没有?"
第3步: 评估复用性 - "能直接用吗?需要小改吗?还是真的没法用?"
```

**示例**:
```typescript
// ❌ 反面示例: 直接写新代码
function NewFeatureScreen() {
  const [camera, setCamera] = useState(null);
  const startCamera = async () => {
    // 100+ 行摄像头逻辑...
  }
  // ...
}

// ✅ 正面示例: 复用现有 Hook
function NewFeatureScreen() {
  const {
    videoRef,
    isActive,
    startCamera,
    toggleCamera
  } = useOCRCamera(); // 复用已有的摄像头 Hook
  // 新功能逻辑只关注差异点
}
```

**可复用资源清单** (当前项目):
- **Hooks**: `hooks/ocr/*`, `hooks/kitMatching/*`, `useVirtualCameras.ts`
- **Components**: `components/ocr/*`, `components/ui/*`
- **Utils**: `utils/*`, `lib/*`
- **Types**: `types/ocr.ts`

### 策略 2: 配置驱动 (Configuration Over Code)

**理念**: 用数据表达逻辑,而不是用代码表达数据

**识别配置化机会**:
| 场景 | 硬编码方式 | 配置化方式 |
|------|-----------|-----------|
| 检测目标不同 | 写 3 个不同的检测函数 | 1 个检测函数 + 目标配置数组 |
| UI 文案差异 | 3 个页面各写一套 JSX | 1 个组件 + 文案配置对象 |
| 业务规则变化 | if-else 堆叠 20 层 | 规则配置 + 规则引擎 |
| 权限控制 | 每个按钮写权限判断 | 权限配置表 + 统一鉴权组件 |

**实战示例**:
```typescript
// ❌ 硬编码: 每种检测模式都要写新代码
function PPEDetection() { /* 200 行代码 */ }
function CleaningDetection() { /* 180 行相似代码 */ }
function KitDetection() { /* 220 行相似代码 */ }

// ✅ 配置驱动: 1 个通用检测器 + 配置
const DETECTION_CONFIGS = {
  ppe: {
    targets: ['helmet', 'vest', 'gloves'],
    threshold: 0.7,
    mode: 'AND',
    resultRenderer: PPEResultDisplay,
  },
  cleaning: {
    targets: ['mop', 'bucket', 'cleaner'],
    threshold: 0.65,
    mode: 'OR',
    resultRenderer: CleaningResultDisplay,
  },
  kit: {
    targets: ['wrench', 'screwdriver'],
    threshold: 0.75,
    mode: 'CUSTOM',
    validator: customKitValidator,
    resultRenderer: KitResultDisplay,
  },
};

function UniversalDetectionScreen({ type }: { type: keyof typeof DETECTION_CONFIGS }) {
  const config = DETECTION_CONFIGS[type];
  const { detect, result } = useYOLODetection(config);
  const ResultComponent = config.resultRenderer;

  return <ResultComponent result={result} />;
}
```

**配置化检查清单**:
- [ ] 是否有 3 处以上重复的常量?
- [ ] 是否有"只是参数不同"的相似函数?
- [ ] 是否有大量 if-else 判断枚举值?
- [ ] 未来是否可能频繁修改这些值?

如果任意一项为"是",考虑配置化。

### 策略 3: 组合优于堆积 (Composition Over Accumulation)

**理念**: 像乐高积木一样拼装功能,而不是在一个文件里堆叠所有代码

**组合模式金字塔**:
```
         ┌─────────────────┐
         │  页面 Screen    │ ← 只负责组装,50-200 行
         │  (组装层)       │
         └────────┬────────┘
                  │
      ┌───────────┴───────────┐
      │                       │
┌─────▼──────┐         ┌─────▼──────┐
│ UI 组件     │         │ 业务 Hook  │ ← 单一职责,100-300 行
│ Components │         │ Hooks      │
└─────┬──────┘         └─────┬──────┘
      │                      │
      └──────────┬───────────┘
                 │
         ┌───────▼────────┐
         │ 工具函数/类型   │ ← 纯逻辑,50-150 行
         │ Utils/Types    │
         └────────────────┘
```

**组合示例**:
```typescript
// ❌ 堆积式: 所有逻辑在一个组件里,6000+ 行
function MegaScreen() {
  // 500 行摄像头逻辑
  // 800 行检测逻辑
  // 1200 行 UI 渲染
  // 1500 行结果处理
  // 2000 行设置面板
  // ...
}

// ✅ 组合式: 拼装已有模块,200 行
function ElegantScreen() {
  // 1. 组合业务 Hooks (每个 Hook 职责单一)
  const camera = useOCRCamera();
  const detection = useYOLODetection({ targets: config.targets });
  const workflow = useOCRWorkflow();
  const history = useOCRHistory();

  // 2. 组合 UI 组件 (每个组件可复用)
  return (
    <ScreenLayout>
      <CameraPreview ref={camera.videoRef} />
      <TargetSelectionPanel
        targets={config.targets}
        onSelect={detection.setTargets}
      />
      <OCRResultDisplay result={detection.result} />
      <DetectionStats stats={detection.stats} />
      <HistoryPanel history={history.records} />
    </ScreenLayout>
  );
}
```

**组合检查点**:
- [ ] 页面主文件是否少于 500 行?
- [ ] 每个 Hook 是否只做一件事?
- [ ] 每个组件是否可以独立使用?
- [ ] 是否能用一句话描述每个模块的职责?

### 策略 4: 替换而非累加 (Replace Over Append)

**理念**: 添加新功能时,考虑能否**替换**掉旧的不够通用的实现

**替换时机识别**:
| 信号 | 含义 | 行动 |
|------|------|------|
| 复制代码 | 发现自己在 copy-paste | ❌ 停止!提取通用方案 |
| 写第 3 个相似函数 | 已经有 2 个功能类似的函数 | 用 1 个通用函数替换掉 3 个 |
| 添加第 5 个 if 分支 | if-else 已经很长 | 重构为配置驱动或策略模式 |
| 文件接近 1000 行 | 单文件增长快 | 拆分模块,用组合替换堆积 |

**替换示例**:
```typescript
// 旧代码: 3 个专用函数 (共 450 行)
function exportOCRResultAsCSV(data: OCRResult) { /* 150 行 */ }
function exportPPEResultAsCSV(data: PPEResult) { /* 150 行 */ }
function exportKitResultAsCSV(data: KitResult) { /* 150 行 */ }

// ❌ 累加思维: 再加一个新功能
function exportCleaningResultAsCSV(data: CleaningResult) { /* 又 150 行 */ }
// 结果: 4 个函数,600 行,维护噩梦

// ✅ 替换思维: 用通用方案替换所有旧函数
function exportAsCSV<T>(
  data: T[],
  columns: ColumnConfig<T>[]
) {
  /* 100 行通用实现 */
}

// 用法: 通过配置解决差异
exportAsCSV(ocrResults, OCR_COLUMNS);
exportAsCSV(ppeResults, PPE_COLUMNS);
exportAsCSV(kitResults, KIT_COLUMNS);
exportAsCSV(cleaningResults, CLEANING_COLUMNS);
// 结果: 1 个函数 + 配置,150 行,轻松维护
```

**替换操作流程**:
```
第1步: 识别重复模式
  ↓
第2步: 设计通用接口 (找出共性,参数化差异)
  ↓
第3步: 实现通用方案
  ↓
第4步: 迁移旧代码到新方案 (逐个替换)
  ↓
第5步: 删除旧代码 (确认无引用后删除)
  ↓
第6步: 更新文档
```

### 决策清单 (Checklist)

在写代码前,先回答这些问题:

**阶段 1: 重用检查** ✅
- [ ] 我搜索过 `hooks/` 目录了吗?
- [ ] 我搜索过 `components/` 目录了吗?
- [ ] 我搜索过 `utils/` 和 `lib/` 目录了吗?
- [ ] 我问过其他同事"有没有类似功能"了吗?
- [ ] 现有模块能否通过**小幅扩展**满足需求?

**阶段 2: 配置化检查** ⚙️
- [ ] 这个功能是否只是"参数不同"?
- [ ] 是否可以用配置对象 + 通用函数实现?
- [ ] 是否可以用**策略模式**代替 if-else?
- [ ] 是否可以用**工厂模式**生成不同实例?

**阶段 3: 组合检查** 🧩
- [ ] 能否拆分为 3 个以下的独立职责?
- [ ] 每个职责是否已有现成 Hook/组件?
- [ ] 能否通过组合现有模块实现?

**阶段 4: 替换检查** 🔄
- [ ] 是否发现了 2+ 个功能相似的旧代码?
- [ ] 能否写一个更通用的方案替换它们?
- [ ] 替换后是否能删除旧代码?
- [ ] 替换后代码总量是否减少?

**阶段 5: 必要性检查** ⚠️
- [ ] 这个功能真的需要吗?(产品需求确认)
- [ ] 能否通过改进现有功能实现?(避免功能冗余)
- [ ] 如果必须写,是否已设计为可复用?

## 💡 具体实施模式

### 模式 1: 策略模式 - 消除 if-else 地狱

**问题场景**:
```typescript
// ❌ if-else 地狱,每加一个检测类型就要改这里
function processDetectionResult(result, type) {
  if (type === 'ppe') {
    // 100 行 PPE 特定逻辑
  } else if (type === 'cleaning') {
    // 100 行 Cleaning 特定逻辑
  } else if (type === 'kit') {
    // 100 行 Kit 特定逻辑
  } else if (type === 'newType') { // 新功能又加 100 行!
    // ...
  }
}
```

**解决方案**:
```typescript
// ✅ 策略模式 - 添加新类型不修改原代码
interface DetectionStrategy {
  validate: (result: DetectionResult) => boolean;
  format: (result: DetectionResult) => FormattedResult;
  render: (result: FormattedResult) => JSX.Element;
}

const DETECTION_STRATEGIES: Record<string, DetectionStrategy> = {
  ppe: {
    validate: (result) => result.score > 0.7 && result.items.length >= 3,
    format: (result) => ({ /* PPE 特定格式 */ }),
    render: (result) => <PPEResultDisplay result={result} />,
  },
  cleaning: {
    validate: (result) => result.score > 0.65,
    format: (result) => ({ /* Cleaning 特定格式 */ }),
    render: (result) => <CleaningResultDisplay result={result} />,
  },
  // 添加新类型:只需添加配置,不修改逻辑代码
  newType: {
    validate: (result) => result.score > 0.8,
    format: (result) => ({ /* 新格式 */ }),
    render: (result) => <NewTypeResultDisplay result={result} />,
  },
};

// 通用处理函数,永远不需要修改
function processDetectionResult(result: DetectionResult, type: string) {
  const strategy = DETECTION_STRATEGIES[type];
  if (!strategy) throw new Error(`Unknown type: ${type}`);

  const isValid = strategy.validate(result);
  const formatted = strategy.format(result);
  return { isValid, formatted, renderer: strategy.render };
}
```

**收益**: 添加新检测类型从"修改 100 行"变成"添加 10 行配置"

### 模式 3: 高阶 Hook - 逻辑复用

**问题场景**:
```typescript
// ❌ 每个检测 Hook 都重复实现加载、错误、重试逻辑
function usePPEDetection() {
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);
  const [retryCount, setRetryCount] = useState(0);

  const detect = async () => {
    setLoading(true);
    setError(null);
    try {
      // PPE 检测逻辑
    } catch (err) {
      setError(err);
      if (retryCount < 3) {
        setRetryCount(retryCount + 1);
        // 重试逻辑
      }
    } finally {
      setLoading(false);
    }
  };

  return { detect, loading, error };
}

// CleaningDetection、KitDetection 也各写一遍相同逻辑...
```

**解决方案**:
```typescript
// ✅ 高阶 Hook - 提取通用的异步处理逻辑
function useAsyncOperation<T>(
  operation: () => Promise<T>,
  options: {
    maxRetries?: number;
    onSuccess?: (data: T) => void;
    onError?: (error: Error) => void;
  } = {}
) {
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<Error | null>(null);
  const [data, setData] = useState<T | null>(null);

  const execute = async () => {
    setLoading(true);
    setError(null);

    let retries = 0;
    while (retries <= (options.maxRetries || 0)) {
      try {
        const result = await operation();
        setData(result);
        options.onSuccess?.(result);
        return result;
      } catch (err) {
        if (retries === (options.maxRetries || 0)) {
          setError(err as Error);
          options.onError?.(err as Error);
          throw err;
        }
        retries++;
        await new Promise(resolve => setTimeout(resolve, 1000 * retries));
      } finally {
        setLoading(false);
      }
    }
  };

  return { execute, loading, error, data };
}

// 所有检测 Hook 都复用这个逻辑
function usePPEDetection() {
  const detectPPE = async () => {
    // 只写核心业务逻辑,不管加载、错误、重试
    return await api.detectPPE(image);
  };

  return useAsyncOperation(detectPPE, {
    maxRetries: 3,
    onSuccess: (data) => console.log('PPE 检测成功', data),
  });
}

function useCleaningDetection() {
  const detectCleaning = async () => {
    return await api.detectCleaning(image);
  };

  return useAsyncOperation(detectCleaning, { maxRetries: 2 });
}
```

**收益**: 每个检测 Hook 从"150 行"减少到"20 行"

### 模式 4: 配置驱动的表单生成

**问题场景**:
```typescript
// ❌ 每个设置面板都手写 JSX,重复代码 800+ 行
function PPESettingsPanel() {
  return (
    <div>
      <Label>检测阈值</Label>
      <Slider value={threshold} onChange={setThreshold} />

      <Label>检测间隔</Label>
      <Input value={interval} onChange={setInterval} />

      {/* 重复 20+ 个表单项... */}
    </div>
  );
}

// CleaningSettingsPanel 又写一遍几乎一样的...
```

**解决方案**:
```typescript
// ✅ 配置驱动的表单生成器
type FieldConfig = {
  name: string;
  label: string;
  type: 'slider' | 'input' | 'select' | 'checkbox';
  defaultValue: any;
  props?: Record<string, any>;
};

const PPE_SETTINGS_FIELDS: FieldConfig[] = [
  {
    name: 'threshold',
    label: '检测阈值',
    type: 'slider',
    defaultValue: 0.7,
    props: { min: 0, max: 1, step: 0.05 },
  },
  {
    name: 'interval',
    label: '检测间隔(ms)',
    type: 'input',
    defaultValue: 1000,
    props: { type: 'number' },
  },
  {
    name: 'mode',
    label: '检测模式',
    type: 'select',
    defaultValue: 'AND',
    props: {
      options: [
        { value: 'AND', label: '全部匹配' },
        { value: 'OR', label: '任意匹配' },
      ],
    },
  },
];

// 通用表单生成器
function DynamicSettingsPanel({ fields, onChange }) {
  const [values, setValues] = useState(
    fields.reduce((acc, field) => ({ ...acc, [field.name]: field.defaultValue }), {})
  );

  const handleChange = (name: string, value: any) => {
    const newValues = { ...values, [name]: value };
    setValues(newValues);
    onChange(newValues);
  };

  return (
    <div>
      {fields.map(field => (
        <FormField
          key={field.name}
          label={field.label}
          type={field.type}
          value={values[field.name]}
          onChange={(value) => handleChange(field.name, value)}
          {...field.props}
        />
      ))}
    </div>
  );
}

// 使用:只需传配置
<DynamicSettingsPanel
  fields={PPE_SETTINGS_FIELDS}
  onChange={handlePPESettingsChange}
/>
```

**收益**: 从"每个面板 800 行"变成"1 个生成器 150 行 + 每个面板 30 行配置"

### 模式 5: 条件导出 - 按需删除功能

**理念**: 添加功能的同时,主动寻找可以**删除**的功能

**✅ 零增长思维**:
```typescript
// 第1步: 识别重复模式
// 发现所有导出都是: 数据数组 → CSV 字符串 → 下载

// 第2步: 设计通用接口
type ColumnConfig<T> = {
  header: string;
  accessor: (item: T) => string | number;
};

// 第3步: 实现通用方案 (100 行)
function exportAsCSV<T>(
  data: T[],
  columns: ColumnConfig<T>[],
  filename: string
) {
  const headers = columns.map(col => col.header).join(',');
  const rows = data.map(item =>
    columns.map(col => col.accessor(item)).join(',')
  );
  const csv = [headers, ...rows].join('\n');

  const blob = new Blob([csv], { type: 'text/csv' });
  const url = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url;
  a.download = filename;
  a.click();
}

// 第4步: 定义各页面的列配置 (每个 10 行)
const PPE_COLUMNS: ColumnConfig<PPEResult>[] = [
  { header: 'ID', accessor: (item) => item.id },
  { header: 'Score', accessor: (item) => item.score },
  // ...
];

// 第5步: 使用 (每个页面 1 行)
exportAsCSV(ppeResults, PPE_COLUMNS, 'ppe-results.csv');
exportAsCSV(cleaningResults, CLEANING_COLUMNS, 'cleaning-results.csv');

// 第6步: 删除旧代码
// 删除 4 个页面中各 150 行的重复代码
```

**成果**:
- **代码量**: 从 600 行 → 150 行 (↓ 75%)
- **维护点**: 从 4 个地方 → 1 个地方
- **添加新导出**: 从"写 150 行"→"写 10 行配置"

## ⚠️ 反模式警示

### 反模式 1: "先实现,后重构"陷阱

**问题**:
```javascript
// "我先快速写完这个功能,有时间再重构"
function NewFeature() {
  // 500 行临时代码...
}

// 现实:永远没有"有时间",代码永远留在那里
// 3 个月后:又基于这 500 行临时代码添加了 1000 行...
```

**正确做法**:
```javascript
// 宁可慢一点,一次性做对
// 第1天:设计接口,复用现有模块
// 第2天:实现核心逻辑,100 行精简代码
// 第3天:测试和文档

// 结果:代码少,质量高,未来不欠技术债
```

**原则**: **没有时间重构,就没有时间写两遍。一次性写对。**

---

### 反模式 2: "万一以后要用"综合症

**问题**:
```typescript
// "虽然现在不用,但万一以后要用呢?"
function TheFeatureThatNeverGetUsed() {
  // 300 行"预留"代码
}

// 现实:3 年过去了,这个函数调用次数 = 0
// 但每次重构都要考虑它,维护成本一直存在
```

**正确做法**:
```typescript
// YAGNI 原则: You Aren't Gonna Need It
// 如果现在不需要,就不要写

// 如果将来真的需要:
// - Git 历史里找回 (如果以前有)
// - 重新写 (可能更好,因为技术进步了)
```

**原则**: **为未来可能的需求写代码,是过度设计。只为当前确定的需求写代码。**

---

### 反模式 3: 过度抽象

**问题**:
```typescript
// 为了"通用",设计了极其复杂的抽象
class AbstractDetectionStrategyFactoryBuilder {
  // 500 行复杂抽象
  // 只为了支持 2 种检测类型...
}

// 结果:
// - 新人完全看不懂
// - 添加新类型反而更复杂
// - 维护成本比重复代码还高
```

**正确做法**:
```typescript
// 平衡:抽象要恰到好处

// 2 个相似功能:允许重复 (DRY 不是绝对的)
// 3 个相似功能:提取简单通用方案
// 5+ 个相似功能:考虑配置驱动或策略模式

// 抽象层次:不超过 3 层
// 通用函数:不超过 5 个参数
// 配置对象:不超过 10 个字段
```

**原则**: **抽象是为了简化,不是为了炫技。如果抽象让代码更难懂,就是过度了。**

---

### 反模式 4: 伪"复用"

**问题**:
```typescript
// "这个函数很通用,可以处理 10 种场景!"
function superGenericFunction(
  data: any,
  type: string,
  mode: string,
  options: any,
  callbacks: any,
  config: any,
  // ...20 个参数
) {
  if (type === 'A') {
    if (mode === 'X') {
      // 分支 1
    } else if (mode === 'Y') {
      // 分支 2
    }
  } else if (type === 'B') {
    // 又是 10 个分支...
  }
  // 800 行 if-else...
}

// 结果:
// - 谁也不敢改
// - 添加新场景要改 10 个地方
// - 维护成本极高
```

**正确做法**:
```typescript
// 真正的复用:清晰的职责边界

// 方案 1: 多个简单函数
function processTypeA(data: TypeAData) { /* 100 行 */ }
function processTypeB(data: TypeBData) { /* 100 行 */ }

// 方案 2: 策略模式 (见前文)
const strategies = {
  A: processTypeA,
  B: processTypeB,
};
```

**原则**: **好的复用是通过组合简单模块,不是通过巨型万能函数。**

### 反模式 5: 复制粘贴驱动开发

**问题**:
```typescript
// 开发者 A: 复制了 PPEScreen 的代码,改成 CleaningScreen
// 开发者 B: 复制了 CleaningScreen 的代码,改成 KitScreen
// 开发者 C: 复制了 KitScreen 的代码,改成 LiveScreen

// 3 个月后发现 PPEScreen 有个 Bug
// 开发者 D: "天呐,我要改 4 个文件..."
// 结果:改了 3 个,漏了 1 个,生产事故
```

**正确做法**:
```typescript
// 第一次写代码:正常实现
// 第二次写相似代码:思考 5 分钟,"能否复用?"
// 第三次写相似代码:必须提取通用方案

// 原则:Rule of Three
// - 1 次:实现
// - 2 次:注意
// - 3 次:重构
```

**原则**: **发现自己在复制代码时,立即停下来,思考能否复用。**

## 💬 总结

### 核心要点回顾

| 策略 | 关键行动 | 预期效果 |
|------|---------|---------|
| **重用优先** | 先搜索,再复用,最后才写新代码 | 新功能 80% 代码来自复用 |
| **配置驱动** | 用数据表达逻辑,不用代码表达数据 | 添加功能只需改配置 |
| **组合优于堆积** | 拼装小模块,不在大文件堆代码 | 页面 < 500 行,模块 < 300 行 |
| **替换而非累加** | 写更通用方案,删除旧代码 | 代码总量不增反减 |

### 最重要的一句话

> **"最好的代码,是不需要写的代码。"**
>
> 在写第一行代码之前,先问自己:
> - 能复用吗?
> - 能配置吗?
> - 能组合吗?
> - 能替换吗?
>
> 如果都不能,再写。
> 如果要写,就写得可复用、可配置、可组合、可替换。

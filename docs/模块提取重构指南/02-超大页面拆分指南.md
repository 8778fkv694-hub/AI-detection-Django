# 超大页面拆分指南

> **目标**: 纯粹为了减少页面行数，即使模块只在当前页面使用，也要提取出来  
> **适用场景**: 页面超过 2000 行，代码难以维护  
> **优先级**: 🔥 **第一优先级**（紧急程度最高，影响面低，复杂度中）  
> **推荐阅读顺序**：第 2 个文档（看完 01-目标与统计 后看这个）

---

## 🧭 拆分前的统一原则（新增）

在动手拆分超大页面之前，建议统一遵守以下原则，避免"越拆越乱"：

### 1. 保持行为完全等价
- 拆分前后，页面对外行为、接口、UI 表现尽量不变。
- 优先只做"搬家 + 拆分"，避免同时引入新功能。

### 2. 优先拆"可复用逻辑"，再拆"仅当前页面使用模块"
- 逻辑 Hook、数据模型、通用 UI 优先抽离，便于其他页面复用。
- 即便只在当前页面使用的 UI 块，也要抽出去减少主文件行数。

### 3. 单一职责 + 清晰命名
- 每个 Hook / 组件只做一件事，例如：
  - `useOCRCamera`：只管摄像头
  - `useOCRHistory`：只管历史记录
  - `OCRSettingsPanel`：只管设置 UI

### 4. 数据结构统一建模
- OCR 结果、AI 分析结果、历史记录记录等，统一在 `types`/`models` 文件中定义，不在页面内随手写类型。

### 5. 所有拆出的模块，都配一小段"用途注释"
- 一句话说明：这个 Hook/组件是干什么的、在哪里被用。

### 6. 每拆完一个模块，做一次最小范围回归检查
- 只验证与这个模块相关的功能点是否正常，避免一次性改太多难以定位问题。

## 📏 超大页面判定标准

| 行数范围 | 等级 | 建议操作 | 优先级 |
|---------|------|---------|--------|
| **< 1000 行** | ✅ 正常 | 无需拆分 | - |
| **1000 - 2000 行** | ⚠️ 较大 | 可考虑拆分，非必需 | 低 |
| **2000 - 3000 行** | 🔶 大 | **建议拆分**，提取重复逻辑 | 中 |
| **3000 - 5000 行** | 🔴 超大 | **强烈建议拆分**，必须提取模块 | 高 |
| **> 5000 行** | 🚨 严重超大 | **立即拆分**，优先处理 | 最高 |

## 📁 推荐目录结构与命名规范（新增）

为避免拆分后文件散乱，建议按照下面的目录结构组织 OCR 相关模块：

```bash
src/
  screens/
    ocrDetection/
      OCRDetectionScreen.tsx
      config.ts           # 当前页面专属配置与常量

  components/
    ocr/
      OCRSettingsPanel/
        index.tsx
        KeywordSettingsSection.tsx
        BarcodeSettingsSection.tsx
        ROISettingsSection.tsx
        YoloSettingsSection.tsx
      OCRResultDisplay.tsx
      QRCodeDetectionResult.tsx
      TargetSelectionPanel.tsx
      DetectionStats.tsx
      ShortcutHelpModal.tsx

  hooks/
    ocr/
      useOCRCamera.ts
      useImagePreprocessing.ts
      useOCRProcessing.ts
      useFusionAI.ts
      useRealtimeDetection.ts
      useOCRWorkflow.ts
      useOCRHistory.ts
      useKeyboardShortcuts.ts

  types/
    ocr.ts                # OCRResult, AIAnalysisResult, HistoryRecord 等
```

**命名规范建议**：
- **Hook**：`useXXX`，明确领域前缀，如 `useOCRXXX`、`useLiveInspectionXXX`。
- **组件**：名词性，例如 `OCRSettingsPanel`、`DetectionStats`。
- **类型 / 接口**：统一在 `types/ocr.ts` 中声明，并在文档中维护。

## 🛠 拆分实施顺序与里程碑（新增）

建议按以下顺序逐步落地，降低风险：

### 第一步：抽离通用类型与配置
- 创建 `types/ocr.ts`、`screens/ocrDetection/config.ts`。

### 第二步：抽离摄像头与图像处理 Hook

### 第三步：抽离 UI 组件
- `OCRSettingsPanel`、`OCRResultDisplay`、`TargetSelectionPanel`、`DetectionStats`、`QRCodeDetectionResult`。
- 把大段 JSX 迁移到对应组件。

### 第四步：抽离工作流和历史记录
- `useOCRWorkflow`、`useOCRHistory`。

- `useKeyboardShortcuts`。

### 第六步：复用到其他页面
- 将 `OCRErrorPreventionScreen`、`KitMatchingScreen`、`LiveInspectionScreen` 中的重复逻辑改为引用通用 Hook / 组件。

## 📌 拆分后的基准页面与联动调整（新增）

超大页面拆分完成后，并不是"结束"，还需要把其他依赖这些逻辑的页面一起对齐、微调。否则会出现：同样的 OCR 逻辑在不同页面行为不一致、Bug 修复只能修一半等问题。

为此建议引入「基准页面」的概念，并按下面的流程推进。

### 1. 明确一个"基准页面"

- **建议将 `OCRDetectionScreen` 作为 OCR 相关逻辑的「基准页面」**：
  - 优先在此页面中拆分、沉淀所有通用 Hook / 组件；
  - 优先在此页面上验证新 Hook、新数据模型、新交互（绿灯后再推广到其它页面）。

- **其它页面**（`OCRErrorPreventionScreen`, `KitMatchingScreen`, `LiveInspectionScreen`）：
  - 尽量通过复用基准页面的 Hook / 组件来实现相同的能力；
  - 只在确实存在业务差异时，才保留自己的定制逻辑。

**简单理解**：
> 「先把 OCRDetectionScreen 拆好、跑通 → 再把其他页面往这个标准上"抄作业"」。

---

### 2. 拆分完成后对其他页面的微调策略

当 `OCRDetectionScreen` 拆分完成并稳定后，建议对其他页面按下面的顺序做对齐和微调：

#### 2.1 Hook 对齐

- 将页面内的「摄像头逻辑」「图像处理」「OCR 调用」「实时检测」「工作流」逐步替换为：
  - `useOCRCamera`
  - `useImagePreprocessing`
  - `useOCRProcessing`
  - `useFusionAI`
  - `useRealtimeDetection`
  - `useOCRWorkflow`
  - `useOCRHistory`
- 如果某个页面确实需要不同的行为，可以在通用 Hook 上增加可配置参数，而不是复制一份逻辑。

#### 2.2 UI 组件对齐

- 使用与基准页面相同的组件：
  - `OCRSettingsPanel`（或其子组件）
  - `OCRResultDisplay`
  - `TargetSelectionPanel`
  - `DetectionStats`
  - `ShortcutHelpModal`
- 若某个页面需要额外字段，可以通过增加 props 的方式扩展，而不是新写一套类似组件。

#### 2.3 数据模型对齐

- 所有页面统一使用 `types/ocr.ts` 中定义的数据结构：
  - `OCRResult`
  - `AIAnalysisResult`
  - `HistoryRecord`
- 页面内不再定义「自家版本」的 OCR 结果类型，避免出现「字段名类似但不完全一致」的问题。

#### 2.4 差异点显式化

- 对于确实和基准页面不一样的逻辑（例如：错误预防页有额外规则，Live 检测页有更轻量的流程）：
  - 在对应 Hook / 组件的参数层面显式体现差异（如 `mode: 'detection' | 'errorPrevention' | 'live'`）；
  - 或在文档中单独记录「该页面与基准页面的差异点」。

---

### 3. 基于"基准页面"的测试策略

因为 `OCRDetectionScreen` 作为基准，所以测试也建议"从基准开始，向外扩散"。

#### 3.1 基准场景（先在 OCRDetectionScreen 上验证）

在 OCRDetectionScreen 上至少要覆盖以下回归场景：

1. **静态图片 OCR**
   - 上传图片 → 预处理 → 手动点击识别 → 查看结果与关键字匹配情况。

2. **摄像头抓拍 OCR**
   - 开启摄像头 → 空格键抓拍 → 自动调用 OCR → 展示结果。

3. **条码 / 二维码识别**
   - 图片或摄像头中包含条码 → 启用条码检测 → 查看条码解析结果。

4. **实时检测**
   - 开启实时检测 → 检查检测间隔、生效阈值、统计数据是否按预期变化。

5. **工作流与状态切换**
   - 从 idle → capturing → processing → waitingConfirm → 下一个样本，这一整套流程是否顺畅。

6. **快捷键行为**
   - Space / Enter / F / R / C / D 是否都触发了文档中描述的行为。

7. **历史记录与导出**
   - 完成几次检测 → 查看历史列表 → 刷新历史 → 导出结果（如有）。

这些场景通过后，可以认为"基准行为"是正确的。

#### 3.2 其他页面的对齐测试

对 `OCRErrorPreventionScreen`, `KitMatchingScreen`, `LiveInspectionScreen`：

- 优先复用同一套 Hook / 组件；
- 然后按以下方式测试：
  - 对于"共享能力"（摄像头、OCR 调用、实时检测、条码识别等），行为应与基准页面保持一致；
  - 对于"页面特有能力"（如错误预防的规则、Kit 匹配的特定校验），只在这些差异点上增加额外用例。

如果发现某个 Bug 同时影响多个页面：

- 优先在基准页面修复（修改 Hook / 组件的内部实现）；
- 再确认其它页面是否也已经切换到了新版本的 Hook / 组件。

---

### 4. 基准升级与版本管理（可选）

当基准页面（OCRDetectionScreen）引入重大改动时，建议：

1. **在文档中记录一次「基准版本升级」**，简单说明：
   - 哪个 Hook / 组件发生了接口变更；
   - 对其它页面有何影响。

2. **对其余页面做一次小范围检查**：
   - 是否都已经使用新的 Hook 参数；
   - 是否有编译告警或运行时逻辑不一致。

这样可以把「超大页面拆分」变成一个相对可控、可迭代的过程，而不是一次性的"搬家工程"。

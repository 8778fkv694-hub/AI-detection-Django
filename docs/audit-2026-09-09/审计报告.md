# OCR 融合与模板驱动生产流程审计报告

审计日期：2026-09-09。审计基线：提交 `2b4e16e31ac3ef1f06cc748bf77f4e7dd67be942` 加当前工作区未提交修改。

## 1. 结论与验收目标

**当前尚不能满足“复杂模板设置好，生产端简单导入即可可靠工作”的目标。** 已具备模板、相机切换、OCR/条码规则、融合判定、多工序与 FQC 的主体功能，但导入、运行、打断、恢复、落库之间缺少完整的一致性保障。正常路径能运行，不代表异常发生后仍不会漏单、串工装或沿用旧判定。

本次记录 **12 项发现：10 项 P1、2 项 P2**。P1 表示在文中触发条件下会影响生产正确性，应在承诺模板驱动生产前解决；P2 表示配置维护、证据与可追溯性缺口。没有把尚未验证的硬件故障推测列成已发生事故。

验收不使用“所有情况下完美”这种不可证明的表述，而采用四条可验证要求：

1. 导入的配置与实际执行一致；无法满足必要条件时，明确停在“未就绪”，不能悄悄换模型、换相机或跳过必检环节。
2. 每件产品、每次检测、每次重试具有清晰身份；上一轮异步结果不得影响下一轮。
3. 异常、缺少证据、未保存成功时不自动放行；恢复后可以确定继续哪件、重做哪步。
4. 模板版本、执行证据、最终结论、人工处理、保存状态能够复盘。

## 3. 当前链路与薄弱边界

`关键词/条码模板 → 工序配方 → 产品工序序列 → 页面导入 → 相机/模型/设备准备 → 采集与ROI缓存 → OCR/条码 → 可选LLM → 前端判定 → 保存 → 后端追踪/FQC → 继续下一件`

当前多个边界由独立 state、ref、effect 和计时器衔接。缺少贯穿全链路的运行标识、配方版本、保存状态与生产轮次，导致各模块局部看起来成功，整条链路仍可能失配。

## 4. 具体发现

### A01 · P1 · 保存回配方遗漏字段，却把本地标成已同步

证据：[保存回配方](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/screens/OCRDetectionScreen.tsx:565)、[本地快照更新](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/screens/OCRDetectionScreen.tsx:606)、[差异检测](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/screens/OCRDetectionScreen.tsx:524)。

`nonGridTargets`、`targetConfidences` 参与差异检测和本地快照更新，却不在 PATCH 请求体中。调整 mini 目标或目标独立置信度，保存成功后提示消失，但重新导入恢复旧值。最小复现已确认请求体与快照不一致。

此外，差异检测漏掉 `keywordMatchMode`、`minConfidence`、`detectionConfidence`、`fixtureEnabled`、相机等字段；仅修改这些内容可能不出现“保存回配方”入口。`fixtureEnabled`、`selectedStandardId` 也未包含在此保存请求中。

修复：统一配置 schema，用同一组字段生成比较、导入和保存；忽略随机 UI id；以服务端返回值更新快照。验收必须逐字段做“编辑→保存→重新加载→执行”闭环。

### A02 · P1 · 工序切换先推进索引，加载失败后仍运行旧配方

证据：[工序加载和切换](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/hooks/ocr/useProductRecipe.ts:42)、[下一步](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/hooks/ocr/useProductRecipe.ts:79)。

下一步先更新索引并提示成功，再异步加载配方。断网、请求失败或配方不存在时只报错，没有回滚。生产端会看到进入下一工序，但实际配置仍为上一工序。

已有请求序号能处理部分“后发请求覆盖先发请求”，但选择“自由模式”不递增序号；退出产品后，尚未返回的旧请求仍可应用工序。产品加载恢复也只恢复产品对象，没有重新校验并应用当前工序。

修复：加载、校验、资源准备全部成功后再一起提交索引与配方；切换期间停用触发；取消选择和卸载也作废请求。切换失败保留原身份并明确提示未切换成功。

### A03 · P1 · 复位不能作废在途 OCR/LLM；旧结果和计时器仍可写回

证据：[强制复位](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/screens/OCRDetectionScreen.tsx:901)、[等待 AI 之后写状态](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/hooks/ocr/useBatchResultHandler.ts:374)、[批次重置](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/hooks/ocr/useBatchProcessingManager.ts:328)、[AI 重置](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/hooks/ocr/useFusionAI.ts:306)。

复位主要清 state/ref，没有共享的取消代号或有效运行检查。`batchRunIdRef` 虽递增，但未用来拒绝过期结果；`resetBatchSaveState` 只清去重字符串。AI 慢响应时按复位，旧回调依然设置合格并调用保存，最小复现已确认。

批次完成、手动完成和确认后还有未登记清理的延时器；用户复位后立即开始新一轮，旧计时器可把新流程设回 idle。更换配方时也没有统一等待或取消在途工作。

修复：引入每轮唯一 `runId` 和取消代号；所有 await 后、UI 写入前、保存/设备输出前校验；复位、换图、换模板、换相机、卸载统一取消。后端不支持取消时，至少拒收旧响应；已经提交的旧记录必须仍归属于旧轮次。

### A05 · P1 · 保存失败不阻止进入下一轮；失败批次可能没有记录

证据：[批次保存异常被吞](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/hooks/ocr/useBatchResultHandler.ts:412)、[普通 OCR 异步保存](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/hooks/ocr/useOCRProcessing.ts:313)、[仅保存成功 OCR 分支](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/hooks/ocr/useDetectionSave.ts:191)。

批次保存异常后仍按检测结论决定自动继续。最小复现：保存函数拒绝后仍显示 qualified，并由计时器转回 idle。普通抓拍与上传路径也不等待保存完成。非融合保存对 `ocrResult.success=false` 不进入保存分支，调用者却可能把 Promise 正常返回视为保存完成。

修复：显式区分“检测完成 / 待保存 / 保存失败 / 已保存”；保存失败保留图片和上下文，支持持久化待提交队列和幂等重试。失败与打断也应保存事件，不能只留成功记录。生产放行必须与持久化确认协调。

### A07 · P1 · FQC 没有工装复用轮次，旧件工序可补齐新件缺检

### A11 · P1 · 后端追踪/FQC降级结论未统一控制前端继续条件

证据：[保存回调](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/screens/OCRDetectionScreen.tsx:335)、[批次合格与继续逻辑](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/hooks/ocr/useBatchResultHandler.ts:395)。

前端先按 OCR/LLM 设置 finalResult。后端保存可能因工装缺失或 FQC 规则降级结果；回调更新追踪展示并控制报警灯，但不更新 finalResult，也不把权威结论返回给批次继续判断。

因此可能出现前端显示合格并自动进入下一件，同时后端记录需复检、报警灯输出异常。具体现场设备时序尚需硬件验证，但两个结论源未闭环在代码中明确可见。

修复：保存函数返回后端最终 disposition，界面、确认状态、计数和设备输出统一使用该结论；前端先显示“初判/待确认”，后端拒绝或超时不得当成最终合格。

### A12 · P2 · 模板关联主要是复制，缺少版本化发布和影响提示

证据：[工装模板选择时复制字段](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/screens/TemplatesScreen.tsx:199)、[工序关键词独立副本](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/backend/inspection/models.py:558)、[运行读取配方映射](/Users/yiliwen/开发/04_比赛与学习/打包带走/改善周项目/AI检测React+Django/src/lib/stageRecipeApi.ts:59)。

选工装模板时复制前缀/正则，工序运行读取复制字段；关键词和条码规则也是副本。修改源模板并不会自动更新已保存工序。复制本身可以是合理的生产冻结策略，但当前没有版本、引用变更提示和重新发布流程，容易让配置人员误以为改源模板已联动到产线。

修复：定义“引用某一版本”或“导入为独立副本”的明确语义。生产锁定发布版本，源模板更新展示受影响工序，经校验发布新版本；当前正在检测的件继续使用原版本快照。

## 6. 生产异常验收矩阵

以下是**整改后的验收清单，不代表此次全部已测试**。用“生命周期阶段 × 异常事件 × 恢复动作”组合扩展，而不是只覆盖用户举出的几例。

| 阶段 | 注入场景 | 必须满足的结果 |
|---|---|---|
| 导入 | 干净浏览器导入完整模板 | 执行参数、设备与模板一致，成功后才可开始 |
| 导入 | 逐字段保存再导入 | 全字段往返一致，随机UI id不制造差异 |
| 导入 | 缺模型、模型标签变更 | 阻止开工，指出具体依赖，不静默回退 |
| 导入 | 相机离线、设备ID变更 | 未就绪，不能拍其他相机却记录指定相机 |
| 导入 | 必需串口未授权/被占用 | 明确未就绪及连接入口 |
| 导入 | 缺标准、融合算力不支持 | 阻止相应模板开工，不跳过必检项 |
| 导入 | URL工序/OCR参数与模板冲突 | 显式拒绝或显示批准后的有效配置 |
| 切换 | A→B加载失败 | A继续保持完整身份，B未成功提示准确 |
| 切换 | A→B→C响应乱序 | 只提交C，A/B不能污染C |
| 切换 | 请求中切自由模式/关闭页面 | 旧请求全部失效 |
| 切换 | 采集/OCR/LLM/保存中换配方 | 明确结束或隔离旧轮次，无混合配置 |
| 采集 | 相机断流、重复旧帧、黑帧 | 停止使用过期图；提示重新采集 |
| 采集 | ROI上传失败、缓存过期 | 重新采集或失败等待，不能永久假就绪 |
| 采集 | 同一目标跨多帧/缺目标 | 按本轮目标完整性判断，不能用旧件补齐 |
| 硬件 | 重复TRIGGER/STOP、分包/粘包 | 每轮单次受理，非法顺序可观测 |
| 硬件 | 未收到STOP/串口拔出 | 明确中断或受控降级；不得假装完成必要动作 |
| 打断 | 每个await前后强制复位 | 旧响应不能更新新轮UI、报警或保存身份 |
| 打断 | 自动重置计时期间开始下一轮 | 旧计时器不能清新轮状态 |
| 打断 | 处理过程中暂停后继续 | 语义明确，不能接收暂停期间不适用的帧 |
| 重启 | 采集中刷新/浏览器崩溃 | 未完成件标中断；清临时缓存/锁，重新校验设备 |
| 重启 | 保存请求发出后崩溃 | 重试同一幂等键，不漏记、不重复 |
| 连续生产 | 连续100件相同文字 | 100条独立记录 |
| 连续生产 | 同一件重复请求/重试 | 只形成一条最终业务记录，保留重试事件 |
| 工装 | A离开、B进入 | 不残留A的视觉码/追踪预览 |
| 工装 | 同一板跨轮次、跨天复用 | 新轮次不能补用旧工序结果 |
| 返工 | 退回上一工序重检 | 明确新尝试与有效版本，原始记录仍可追溯 |
| 保存 | 断网、500、超时、响应丢失 | 不放行；保留待保存数据并幂等恢复 |
| 保存 | OCR失败/部分ROI失败 | 有失败记录与证据，不能“保存成功”但无记录 |
| 终检 | 缺工装/缺工序/规则不符 | UI、数据库、报警、自动继续采用同一结论 |
| 终检 | 多产品共用同一FQC工序 | 按明确产品实例归并，不取任意产品 |
| 人工 | 手动放行、复位、返工 | 区分动作含义，记录原因及执行人；不篡改原判定 |
| 并发 | 双窗口同流不同模型与模板 | 状态、缓存、记录、停止操作不串扰 |
| 耐久 | 存储满、服务重启、长期运行 | 有界缓存/重试、明确告警和可执行恢复入口 |

验收记录应保留：配方版本、运行ID、事件时间线、实际设备/模型、请求响应、结果ID和预期/实际差异。对所有异常至少测试“异常发生→人工恢复→下一件正常完成”，不能只测异常提示是否出现。

## 7. 建议的整改结构与顺序

### 第一批：先防漏单、串件和旧结果回写

解决 A03/A04/A05/A06/A07/A11。建立检测运行ID、工装装载轮次、统一作废机制、保存幂等及最终结论闭环。回归加入本次缺陷复现的反向断言，再覆盖异常恢复后的下一件。

### 第二批：实现可信的模板一键导入

解决 A01/A02/A08/A09。导入作为事务执行：读取发布模板→验证参数/引用→准备相机模型设备→一次性提交有效配置→进入就绪。页面重启走同一条恢复/校验入口，不能分散恢复一部分字段。

操作员只需要看到“选择模板→就绪→开始”，异常时提供明确的“重新连接 / 重试保存 / 重新采集 / 结束本件”动作。底层复杂性由系统承担，不要求操作员逐个排查开关。

### 第三批：配置治理、证据和硬件耐久验证

解决 A10/A12，建立模板版本、证据快照和发布影响分析。补充实际Jetson、摄像头和串口故障注入及耐久运行；测试界面绿色、后台记录与物理输出一致。

建议状态流：

`未配置 → 校验中 → 就绪 → 采集中 → 分析中 → 保存中 → 已完成/需人工处理`

另有显式 `暂停 / 中断 / 故障 / 待保存` 状态。任何继续或复位都必须说明结束哪个运行、清哪些瞬时数据、保留哪些业务记录；“清空页面”不能代替业务取消。

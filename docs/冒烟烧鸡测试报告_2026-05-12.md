# AI检测系统 — 冒烟+烧鸡测试报告

> **测试时间**: 2026-05-12
> **测试方法**: 代码级全链路追踪，模拟用户完整操作流程
> **测试范围**: 开机→选模型→配流媒体→设参数→检测→保存→长期运行

---

## 一、冒烟测试（首次开机完整链路）

### S1 🔴 冷启动模型未就绪

**场景**: 开机 → 打开页面 → 模型显示「未知」

**根因**: `useCurrentModel()` 只在组件 mount 时调用一次 `getAvailableModels()`。如果后端模型池还未预热（YOLO 冷启动需 2-5 秒），返回空池，`currentModel = 'unknown'`。前端没有重试机制。

**影响**: 用户第一次开机必然看不到模型，不知道要等多久。

**文件**: `src/hooks/useCurrentModel.ts:39-41`

---

### S2 🔴 模型 ID 在检测链路中可能丢失

**场景**: 用户选了 PPE 模型，检测时后端跑的是默认模型

**根因**: `useRealtimeDetectionLoop` 传 `model_id: currentModelId || undefined`。当 `currentModelId` 为 `null` 时被转为 `undefined`，后端 `yolo_detect` 回退到 `get_default_model_id()`。

**影响**: 用户以为是 PPE 检测，实际可能跑的是水机检测模型。

**文件**: `src/hooks/ocr/useRealtimeDetectionLoop.ts` yoloDetectBackend 调用处

---

### S3 🟡 保存检测结果静默失败

**场景**: 检测完成 → 点保存 → 没报错但数据没入库

**根因**: `useDetectionSave.saveDetectionResult()` → `addAppResult()` → POST `/api/results/`。网络抖动或 DB 锁导致 500 时，catch 只打 `console.log`，不弹 toast。

**影响**: 质检员以为保存成功，实际数据丢了。下次查记录找不到。

**文件**: `src/hooks/ocr/useDetectionSave.ts:145`

---

### S4 🟡 先开检测再开摄像头 = 无效操作

**场景**: 用户操作顺序错了 → 先点「开始检测」→ 再开摄像头

**根因**: 检测循环不检查流状态。`StreamReader` 未启动时 `get_frame_ref()` 返回 None，检测循环空转。

**影响**: 画面出来了但没有检测框，用户困惑。

**文件**: `src/hooks/ocr/useRealtimeDetectionLoop.ts` + `backend/inspection/detection_loop.py`

---

### S5 🟡 检测中应用配方 → 在飞任务用旧参数

**场景**: 正在跑检测 → 用户点配方应用 → 新配方改了 `selectedTargets`

**根因**: `applyRecipe` 调 `setSelectedTargets` 更新 state，但 `detectionQueueRef` 里排队的任务捕获的是旧闭包值。

**影响**: 配方切换后前几轮检测仍用旧目标列表，触发逻辑混乱。

**文件**: `src/screens/OCRDetectionScreen.tsx:460-500`

---

### S6 🟡 配方切模型 → 前后端不同步

**场景**: 配方带了新模型 ID → `setCurrentModelId` 触发前端重载配置 → 但后端 detection loop 还在用旧模型

**根因**: 前端 `useModelConfig` 通过 `getModelConfig` 重新加载了配置，但后端的 `DetectionLoop` 没有收到 `update_config` 通知。

**影响**: 前端显示新模型的检测目标，后端用旧模型推理。结果对不上。

**文件**: `src/screens/OCRDetectionScreen.tsx:473-474` + `backend/inspection/detection_loop.py:68-75`

## 二、烧鸡测试（24h 连续运行 + 异常场景）

### B1 🔴 HLS TS 文件堆积 → 磁盘满

**场景**: HLS 流 7×24 不间断转码

**根因**: H2 修复了 `stop()` 时清理。但 running 期间的清理依赖 ffmpeg 的 `delete_segments` 参数。如果 ffmpeg 被 OOM Killer 杀掉或异常退出，清理来不及执行。`media/hls/` 下残留 .ts 文件只增不减。24h × 15fps HLS ≈ 86,400 个 TS 文件。

**影响**: Jetson 磁盘（通常 64GB eMMC）几小时就满。

**文件**: `backend/inspection/stream_hls.py:246-249`

---

### B2 🔴 MJPEG ↔ cv2 反复切换 → 僵尸线程堆积

**场景**: 工人在 MJPEG 预览和检测模式之间切换，或频繁刷新页面

**根因**: 每次 MJPEG 结束，`_restart_cv2_reader` 创建新的 `StreamReader`。旧 reader 的 `stop()` 调了 `thread.join(timeout=2.0)`，但 `_read_loop` 可能卡在 `cap.read()` 阻塞调用中，2 秒超时后线程没死。100 次切换 = 100 个僵尸线程。

**影响**: Jetson 线程数爆炸，最终无法创建新线程。

**文件**: `backend/inspection/mjpeg_passthrough.py:287-300` + `backend/inspection/stream_service.py:69-74`

---

### B3 🔴 多窗口并发保存 → database is locked

**场景**: 两个质检员同时操作，各自的检测结果同时保存

**根因**: SQLite 默认 journal mode 是 DELETE，写操作串行。两个请求同时 INSERT → 第二个报 `database is locked`。审计报告 #10 和上线清单 #10 都提到了，建议 `PRAGMA journal_mode=WAL`。

**影响**: 并发场景下随机丢数据。

**文件**: `backend/config/settings.py` (SQLite 配置)

---

### B4 🔴 统计页面全表扫描 → 页面卡死

**场景**: 运营打开统计页面，查 3 个月数据

**根因**: `ppe_stats` 端点：`InspectionResult.objects.all()` 无分页，然后三次 `.count()` 各扫全表。SQLite 上锁住整个 DB。

**影响**: 统计页面打开时整个系统不可用（DB 被锁）。

**文件**: `backend/inspection/views.py:718-739`

---

### B5 🟡 连续切 3 个 YOLO 模型 → Jetson OOM

**场景**: 用户在工作流中切换 PPE → 滤芯 → 水机检测

**根因**: `MAX_MODEL_POOL_SIZE = 3`。每个 YOLO 模型约 1.5-2GB 显存。Jetson Orin Nano 8GB 共享内存，3 个模型 + OCR 模型 + 系统开销 → OOM。

**影响**: Jetson 卡死或进程被 OOM Killer 杀掉。

**文件**: `backend/inspection/yolo.py:18`

---

### B6 🟡 摄像头断连 → 重连策略退化

**场景**: 网线被踢、摄像头重启、电磁干扰

**根因**: `_read_loop` 里重连间隔固定 `reconnect_interval`（默认 5 秒），无指数退避。审计报告 #8 已提未修。

**影响**: 连续断连时每 5 秒 CPU 空转重试，不增加间隔。

**文件**: `backend/inspection/stream_service.py:228`

---

### B7 🟡 检测记录只增不删 → DB 无限增长

**场景**: 工厂连续运行 3 个月，每天 1000 条检测

**根因**: 没有归档或清理机制。`InspectionResult` 表无分区、无 TTL。90,000 条后查询越来越慢。

**影响**: 查询慢 → 页面卡 → 用户体验崩溃。

**文件**: `backend/inspection/models.py:373` (InspectionResult 模型)

---

### B8 🟡 OCR/QR 模型常驻内存 → 无法释放

**场景**: 使用了一次 OCR 功能后，模型永远占用内存

**根因**: `OCRService` 和 `WeChatQRService` 是模块级单例，模型加载后无卸载接口。

**影响**: 即使不再用 OCR，RapidOCR 的 3 个 ONNX 模型（~200MB）仍占用 RAM。

**文件**: `backend/inspection/ocr_service.py:46` + `backend/inspection/wechat_qr_service.py:17`

---

### B9 🟢 low_latency 模式连读 50 帧 → 偶发卡顿

**场景**: 低延迟模式下，`_read_loop` 一次清空 50 帧缓冲区

**根因**: `for _ in range(50): cap.read()` 在单次循环中执行，期间 read loop 阻塞。审计报告 #18 已提未修。

**影响**: 偶发性的 100-200ms 延迟抖动。

**文件**: `backend/inspection/stream_service.py:239`

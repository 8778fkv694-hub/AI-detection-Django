## 1. 逐条应对蓝军隐患

### 1.1 应对隐患一：JPEG 编码阻塞检测线程

**蓝军判定**：⚠️ **完全成立，必须修正**

这是蓝军最有价值的发现。在 Orin Nano ARM 核上 `cv2.imencode` 1080p 需 80-150ms，放在 YOLO 循环里会把检测从 30fps 拖到 7fps。

**修正方案：检测线程只存 NumPy 引用，按需编码**

```python
def _detect_loop(self):
    while self.is_running:
        frame = reader.get_frame_ref()   # 零拷贝取帧
        boxes = run_inference(frame)     # GPU ~30ms

        with self._lock:
            self._frame_id += 1
            self._latest_raw_frame = frame   # 存 NumPy 引用（零 CPU 开销）
            self._latest_result = {
                'frame_id': self._frame_id,
                'boxes': boxes, ...
            }
            # 绝不在这里做 cv2.imencode

def get_snapshot_jpeg(self, requested_frame_id=None):
    """仅在 /snapshot/ 被请求时才编码（在 Django worker 线程中执行）"""
    with self._lock:
        frame = self._latest_raw_frame
        actual_id = self._frame_id
    if frame is None:
        return None, None
    # 编码在 Django worker 线程，不阻塞检测线程
    _, jpeg = cv2.imencode('.jpg', frame, [cv2.IMWRITE_JPEG_QUALITY, 95])
    return jpeg.tobytes(), actual_id
```

**性能影响**：
- 检测线程：只做推理 ~30ms/帧，理论上限 ~30fps ✅
- `/snapshot/` 按需压缩：每次 80-150ms，但频率极低（仅抓拍时调用）✅
- 内存代价：多存一个 NumPy 数组 ~6MB，Orin Nano 8GB 完全可接受 ✅

### 1.2 应对隐患二：幽灵漂移（帧-框时序错位）

**蓝军判定**：⚠️ **原理成立，但严重程度需降级**

**降级理由**：
1. 你的产线是**静态或缓慢移动**的检测场景，不是高速飞拍
2. 现有前端延迟 >600ms（500ms 轮询 + 100ms 网络），改造后 200ms 偏移是巨大进步
3. 从代码看 `captureDelaySeconds` 可配置 0-N 秒，业务容忍度远大于 200ms

**但仍然要防（成本极低）**：

```python
# /detections/ 返回值增加 frame_id
{
    "frame_id": 12345,
    "boxes": [...],
    "detect_fps": 22.5
}

# /snapshot/?frame_id=12345
# 后端确保返回产生检测框的那一帧
# 只缓存最近 1 帧（6MB），不做环形缓冲
```

**为什么不做环形缓冲**：
- 1080p BGR 帧 ~6MB，缓存 30 帧 = 180MB，性价比太低
- 你的场景帧生命周期极短（<100ms），缓存命中率极低
- 1 帧缓存 + frame_id 足以覆盖业务需求

**推荐方案 A（根本解决）**：把延时抓拍的帧采集下沉到后端

let prevUrl: string | null = null;

### 1.4 应对隐患四：HTTP 轮询风暴

**蓝军判定**：⚠️ **过度渲染**

蓝军计算有误。`/detections/` 是纯内存读取 + JSON 序列化（<1ms）。3 摄像头 x 5fps = 15 请求/秒 x 1ms = **1.5% CPU**，不至于"打挂"。

**修正：采用分级轮询频率**

| 工作流状态 | 轮询频率 | 理由 |
|:---|:---:|:---|
| idle（等待目标） | 5fps | OR/AND 判断不需要更快 |
| debouncing（防抖中） | 10fps | 需要快速响应 |
| capturing / processing | **停止轮询** | 不需要新检测结果 |

**WebSocket 备选**：作为二期优化，但目前 HTTP 轮询 + 分级频率已足够。

---

### 1.5 应对隐患五：模型换页假死

**蓝军判定**：⚠️ **合理担忧，已有防护**

`yolo.py` 的 `MAX_POOL_SIZE=3` 覆盖 3 路摄像头。多数情况用同一模型。

**补强**：启动检测循环时显式校验模型池容量：

```python
def start_loop(self, stream_id, model_id, conf):
    active_models = set(l.model_id for l in self.loops.values() if l.is_running)
    from .yolo import MAX_POOL_SIZE
    if len(active_models) >= MAX_POOL_SIZE and model_id not in active_models:
        raise ValueError(f"模型池已满({len(active_models)}/{MAX_POOL_SIZE})")
```

## 2. 蓝军遗漏的问题（白军补充发现）

### 2.1 遗漏一：`get_frame()` 每次 `.copy()` 6MB

`stream_service.py` 第 288 行：

```python
def get_frame(self):
    with self.lock:
        return self.current_frame.copy() if self.current_frame is not None else None
```

检测线程 30fps x 6MB = **180MB/秒内存拷贝**。

**修正**：新增 `get_frame_ref()` 返回引用（零拷贝）：

```python
def get_frame_ref(self):
    """返回帧引用（零拷贝），仅供只读消费者"""
    with self.lock:
        return self.current_frame  # 直接返回引用
```

`_read_loop` 写入时是 `self.current_frame = frame`（整体替换引用），读线程拿到的引用指向的旧数组不会被修改，线程安全。

### 2.2 遗漏二：MJPEG 画框坐标缩放顺序

`mjpeg_view.py` 中必须保证：**先叠加检测框（在原始分辨率上），再做 resize**。如果反了，框坐标会错位。

## 3. 工作流完整性分析（对解耦的全面风险评估）

> 用户关切：解耦后，拉普拉斯清晰度评估、ROI裁剪、拼接、OCR、二维码检测这一整套工作流能否正确运行？

### 3.1 当前工作流全链路

```
YOLO 检测 → OR/AND 判断 → 防抖 → 触发抓拍
    → 帧采集（延时模式：200ms间隔持续截图）
    → 拉普拉斯清晰度评估（每个ROI独立评分）
    → 选出最清晰的那帧的ROI
    → 批处理路径：
        → cacheROI() 上传每个ROI到后端
        → checkAllTargetsReady() 确认全部到齐
        → triggerBatchProcessing()
            → batch_detection_service.py
            → 每个ROI → OCR(PaddleOCR) + 条码检测(pyzbar)
            → 关键词验证 + 条码验证
            → 合并结果 → 返回 overall_quality
    → 非批处理路径：
        → stitchROISnapshots() 拼接
        → processCapturedImage() AI分析
```

### 3.2 解耦后的影响矩阵

| 工作流步骤 | 当前实现位置 | 解耦后变化 | 风险等级 |
|:---|:---|:---|:---:|
| **YOLO 检测** | 前端截图上传 | → 后端持续检测，前端拉 JSON | ✅ 无风险 |
| **OR/AND 判断** | 前端 `evaluateDetections()` | **不变** — 输入仍是 boxes 数组 | ✅ 无风险 |
| **防抖** | 前端 `evaluateDebounce()` | **不变** — 输入仍是 boolean | ✅ 无风险 |
| **帧采集（延时模式）** | 前端 `drawImage()` 200ms 循环 | ⚠️ 需要适配 — 改为后端提供帧 | 🟡 中风险 |
| **拉普拉斯清晰度** | 前端 `calculateSharpnessAsync()` | ⚠️ 需要适配 — 图片来源变了 | 🟡 中风险 |
| **ROI 裁剪** | 前端 `batchExtractROIs()` | ⚠️ 需要适配 — 用后端帧裁剪 | 🟡 中风险 |
| **ROI 缓存上传** | 前端 `cacheROI()` → 后端 `/api/yolo/cache-roi/` | **不变** — 上传 dataUrl 到后端 | ✅ 无风险 |
| **批处理触发** | 前端 `triggerBatchProcessing()` | **不变** — 纯前端状态判断 | ✅ 无风险 |
| **OCR + 条码检测** | 后端 `batch_detection_service.py` | **完全不变** — 后端独立模块 | ✅ 无风险 |
| **关键词/条码验证** | 后端 `_validate_roi()` | **完全不变** | ✅ 无风险 |
| **结果合并** | 后端 `_merge_results()` | **完全不变** | ✅ 无风险 |
| **Canvas 画框** | 前端 `drawDetections()` | → 后端 MJPEG 画框，前端可选关闭 | ✅ 无风险 |

### 3.3 中风险项的精确处理策略

#### 帧采集（延时模式）— 两种策略

**策略 A（推荐，最安全）：保留前端帧采集，但改数据来源**

```
现在：前端 drawImage(video) → 前端 canvas → 前端 toDataURL
改为：前端 fetch(/snapshot/) → 前端拿到 JPEG → 前端 Image → 前端 canvas
```

这样后续的清晰度评估、ROI裁剪代码**一行不改**。风险最低。

**策略 B（激进，性能最优）：帧采集也下沉后端**

新增后端 API `/api/streams/<id>/capture-best-frame/`，后端内部做清晰度评估。
好处是前端不碰帧数据，但需要把 `calculateSharpnessAsync` 移植到 Python（拉普拉斯方差）。

**一期用策略 A，二期有需要再升级到 B。**

#### 拉普拉斯清晰度评估 — 无需修改

```typescript
// useROIProcessor.ts 中的 calculateSharpnessAsync()
// 输入：ImageData（来自 canvas.getImageData()）
// 输出：清晰度分数 number

// 关键：不管图片来自前端截图还是后端 /snapshot/，
// 只要最终塞进 canvas 里拿到 ImageData，清晰度计算逻辑完全不变
```

#### ROI 裁剪 — 只需确保坐标和帧一致

```typescript
// batchExtractROIs() 的输入：
//   detections: BackendYoloDetection[]  ← 来自 /detections/
//   dataUrl: string                     ← 来自 /snapshot/?frame_id=xxx

// 关键：frame_id 机制保证 detections 和 dataUrl 是同一帧
// 裁剪逻辑本身不需要任何修改
```

### 对工作流完整性的结论

**解耦的核心边界是清晰的**：
- YOLO 检测数据来源变了（前端截图 → 后端 JSON），但下游的**所有业务逻辑（判断、抓拍、清晰度、裁剪、拼接、OCR、验证）的代码和接口完全不变**。
- 唯一需要适配的是帧采集的图片来源（从 `<video>` 元素改为后端 `/snapshot/`），而且可以用策略 A（最安全的改法）做到下游代码一行不改。
- 采用 `frame_id` 机制绑定帧和检测框，消除异步时序风险。

**这套解耦不是"大手术"，而是"改水管接口"**——管道里流的水（boxes 数组、ROI 图片、OCR 文本）格式不变，只是水的来源从前端水泵改成了后端水泵。

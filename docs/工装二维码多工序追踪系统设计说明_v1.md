# 工装二维码多工序追踪系统设计说明 v1

## 1. 背景与目标

本方案用于在现有 React + Django AI 检测系统中，增加基于工装二维码的多工序追踪与规则校验能力。

现场前提如下：

- 产品始终和工装一起流转
- 如需换板，二维码也必须随产品一起转移
- 同一时刻现场会有多块工装同时流转
- 不同工序页面会同时打开
- 不同工序上的业务编码可能不同，但它们之间存在明确的映射规则

系统目标：

- 用工装二维码作为同一件在制品的追踪键
- 支持多个页面、多个工序同时采集
- 各工序结果按同一工装二维码自动归并
- 根据配置规则执行跨工序匹配校验
- 在最终结果中输出追踪说明、工序标识、工装二维码及规则明细

## 2. 核心设计原则

### 2.1 追踪键

`fixture_qr` 作为在制品流程追踪码。

说明：

- 业务上叫工装二维码
- 系统上作为当前产品流程的唯一追踪键
- 不要求固定只能通过视觉识别，可由多种输入方式提供

### 2.2 工装二维码统一输入

工装二维码只是一个统一输入字段，允许多来源输入：

- `vision`：视觉抓拍识别
- `scanner`：扫码枪输入
- `nfc`：NFC 读取
- `manual`：人工输入

第一版默认优先使用 `vision`，尽量不增加新设备。

### 2.3 页面职责

每个工序页面只负责：

- 获取工装二维码
- 识别本工序业务编码、OCR 结果、条码结果、外观结果
- 上报当前工序结果
- 展示当前工装二维码关联的全流程状态

页面不负责做跨工序最终规则判断，跨工序判断统一在后端完成。

### 2.4 判定原则

- 证据充分才判 `合格`
- 识别缺失、规则失败、信息冲突、关联不稳时判 `需复检`
- 不使用时间猜测代替二维码归并

## 3. 业务规则

### 3.1 现场硬规则

- 一码一板：同一时刻一个二维码只能对应一块工装
- 一板一码：同一时刻一块工装只能有一个有效二维码
- 码随产品走：换板时二维码必须同步转移
- 无码不判定：未识别到工装二维码，不允许进入正式追踪判断
- 冲突即复检：同一码出现不合理并发或结果冲突时直接 `需复检`
- 低置信度不流转：关键识别不稳定时不允许自动判定 `合格`

### 3.2 工装二维码输入规则

工装二维码必须至少满足以下规则：

- 必填
- 格式合法
- 来源明确
- 状态明确
- 若来源为视觉，置信度达到阈值

## 4. 系统架构

系统分为三层：

### 4.1 采集层

由各工序页面负责：

- 工装二维码输入
- 当前工序业务码识别
- OCR/条码/视觉检测
- 结果上报

### 4.2 归并层

后端根据 `fixture_qr` 将多工序结果归并为同一条追踪链。

归并内容包括：

- 当前工装二维码
- 当前工序记录
- 其他已完成工序记录
- 当前追踪状态

### 4.3 规则层

后端按规则配置执行：

- 工装二维码规则
- 跨工序规则
- 最终追踪结论计算

第一版优先采用最小改造方式：在现有检测结果模型上扩字段。

如果后续需要完整的流程追踪中心，再拆分独立表。

## 7. 页面参数设计

每个页面必须明确自己的工序身份。

建议通过 URL 或页面配置传入：

- `stage_code`
- `stage_name`
- `page_instance_id`
- `camera_id`

示例：

```text
/ocr-detection?stage_code=step_1&stage_name=工序1&camera_id=cam_1&page_instance_id=page_1
/ocr-detection?stage_code=step_2&stage_name=工序2&camera_id=cam_2&page_instance_id=page_2
```

页面内部读取后，作为当前检测结果的固定字段参与保存与上报。

## 8. 规则设计

规则分为两大类：

### 8.1 工装二维码规则 `fixture_rule`

用于判断当前工装二维码本身是否有效。

建议第一版支持：

#### 规则 1：必填

- `fixture_qr` 为空，直接 `需复检`

#### 规则 2：输入成功

- `fixture_qr_input_status != success`，直接 `需复检`

#### 规则 3：格式合法

- 二维码内容需满足约定格式，例如 `^FIXTURE-[0-9]{4}$`

#### 规则 4：视觉来源置信度

- 当 `fixture_qr_source = vision` 时，`fixture_qr_confidence` 必须达到阈值

### 8.2 跨工序规则 `trace_rule`

用于比较不同工序间的业务编码或字段关系。

建议第一版支持：

- `equals`
- `contains`
- `transform_equals`

推荐至少支持一种转换规则：

- `keep_last_6_digits`

### 8.3 示例规则

工装二维码规则：

```json
{
  "ruleId": "fixture_required",
  "ruleType": "fixture_rule",
  "ruleName": "工装二维码必填",
  "operator": "required",
  "onFail": "需复检"
}
```

跨工序规则：

```json
{
  "ruleId": "step1_to_step2_code_match",
  "ruleType": "trace_rule",
  "ruleName": "工序1到工序2编码匹配",
  "sourceStage": "step_1",
  "sourceField": "businessCode",
  "targetStage": "step_2",
  "targetField": "businessCode",
  "operator": "transform_equals",
  "sourceTransform": "keep_last_6_digits",
  "targetTransform": "keep_last_6_digits",
  "onMissing": "需复检",
  "onFail": "需复检"
}
```

## 11. 追踪结论合并策略

最终结果需要同时考虑：

- 当前页面原有 OCR/条码/AI 结论
- 新增的追踪结论

建议规则：

- 如果 `traceConclusion = 需复检`，则最终结果不得高于 `需复检`
- 如果当前页面检测为 `合格`，但追踪规则失败，则最终仍取 `需复检`

原因：

- 单工序图像合格，不代表跨工序流程关系成立

## 16. 结论

本方案以工装二维码为统一追踪键，以工序标识为页面上下文，以规则配置为跨工序判断依据。

第一版采用最小改造方式：

- 不重写原有检测链路
- 只增加追踪相关字段、规则与结果说明
- 先支持视觉抓拍方式输入工装二维码
- 为扫码枪和 NFC 等输入方式预留统一字段结构

这样可以在不显著增加现场设备投入的前提下，先把多工序追踪能力稳定落地。
